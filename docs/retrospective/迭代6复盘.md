# 迭代 6 复盘：批量重复运行与评测标定

## 一、迭代目标

解决当前平台“只能跑单次运行、无法量化随机性与稳定性”的问题：
1. **支持单场景重复运行（Repeat）**与**多场景批量运行（Batch）**；
2. **量化方差与科学性标定（Variance & Judge Calibration）**：耗时分布、工具调用频次/方差、交互轮次、Judge 稳定性；
3. **统一批次产物与 API 控制面**：`reports/batches/<batch_id>/`、`/api/batches` 与 SSE 实时事件。

## 三、最终复盘与总结

### 1. 核心收获与解决的问题
- **从“单次随机运行”迈向“统计学可靠评测”**：引入 `repeat_count` 与 `BatchRunner`，使 GeoSkillBench 能够衡量 Agent 在相同任务下的稳定度（Pass Rate、轨迹熵、耗时分布），消除了单次随机波动对评测结论的干扰。
- **多维度过程方差量化**：不仅统计最终成败，更通过工具调用频次分布、轨迹离散度（Shannon Entropy）、对话轮次分布深入分析 Agent 的行为漂移。
- **完备的产物与控制面闭环**：
  - 文件系统：`reports/batches/<batch_id>/summary.json` 与 `summary.md` 独立留痕；
  - 数据库：`batches` 表持久化聚合结果并与子 run 建立关联；
  - API & SSE：支持前后端全异步批量下发与实时事件广播。

### 2. 遗留事项与后续方向（迭代 7+）
- 当前批次调度默认采用串行调度（`concurrency=1`），后续可根据外部 GIS 服务承载能力平滑引入并发池；
- 下一步（迭代 7）可在此统计基座上，深入拓展空间关系规则（`spatial_relation`）、几何拓扑有效性等 GIS 领域特色确定性断言。
- 迭代 6 收尾时前端仍无 Batch 入口；该项在 6.1 一并补上，见下文。

# 附录：迭代 6.1 复盘（批次横向 AI 诊断）

> 状态：**已完成（2026-09-02）**。接在迭代 6 统计基座上，不另开独立复盘文件。
> 计划：[../plan/迭代6.1-多维度AI诊断与标定引擎.md](../plan/迭代6.1-多维度AI诊断与标定引擎.md)
> 活设计：[../design/05-批次AI诊断.md](../design/05-批次AI诊断.md)

## 一、目标

解决“连续重复运行 N 次后，只有数字、没有横向归因”的缺口：

1. 对整个 batch 做一次手动 AI 诊断（根因占比 + 文字分析）；
2. 主因是 Skill 时给出可复制的 unified diff，**绝不写回** `skills/`；
3. 控制台能看见批次、轮次进度和诊断结果。

明确不做：自动改 Skill / 断言 / 容差、GIS 拓扑诊断、单次 run 深度诊断、全站导航重构、DB schema、batch 完成时自动分析。

## 二、执行记录

### 第 1 步：数据模型与输入组装
- **状态**：**已完成**
- 诊断结构放进 `geoskillbench.models.batch`：`BatchAIDiagnostics`、`SkillPatchSuggestion`。
- 归因枚举冻结：`skill_prompt_issue` / `agent_drift` / `env_error` / `assertion_or_scenario` / `harness_variance` / `unknown`。
- `assemble_analyst_input` 喂三层：批次聚合、最多 20 条压缩 run（工具序列 + 失败断言）、Skill 原文。草稿只喂 `pass_rate`/`entropy` 的路径废弃。

### 第 2 步：Analyst 引擎与 API
- **状态**：**已完成**
- `geoskillbench/runtime/batch_analyst.py` 重写：复用 `extract_json`；归因 key/总和校验失败则降为 `{unknown: 1.0}`。
- Patch 门控：唯一 Skill 且 `skill_prompt_issue ≥ 0.4`，且 LLM 给出基于原文的完整文件，后端 `difflib` 生成真实 diff。假 fallback（写死 buffer 补丁）删除。
- LLM 失败 → `source=unavailable` 占位（无归因、无 patch），写 `ai_diagnostics.json` 后 API **502**。
- `POST /api/batches/{id}/analyze`、`GET .../diagnostics`；运行中 409；无 summary 404；覆盖写盘；补了 `import json`。不改 `batches` 表。

### 第 3 步：前端 Batch 面板
- **状态**：**已完成**
- `App.jsx`：Scenario 旁 Repeat +「创建批次」；顺序为 Scenario → Progress → Batches。
- 创建批次后订阅 `/api/batches/{id}/events`，Progress 显示第 N/M 轮、已完成数和当前子 run 阶段。
- `BatchAnalystView`：简报、归因条、Diff + 复制。统计改卡片，去掉 JSON 墙。

### 第 4 步：测试与文档
- **状态**：**已完成（单测 mock LLM；真机诊断未跑）**
- `tests/test_batch_analyst.py`：解析、归因校验、patch 门控、unavailable、不写 `skills/`。
- `tests/test_batch_api.py`：404 / 写盘 / 502 占位。
- 活文档：`docs/design/05-批次AI诊断.md`；`docs/design/00` 记 v0.6。

## 三、结论

### 1. 做成了什么
- 诊断是辅助层，正式 verdict / pass_rate 仍只看硬断言和批次聚合。
- Patch 从“LLM 瞎编 diff”改成“原文 → 完整文件 → 后端生成 unified diff”，并禁止写回磁盘。
- 迭代 6 留下的“前端无 Batch 入口”补上了：能创建、看轮次、看诊断。

### 2. 实施中纠正的偏差
- 第一版草稿（`batch_analyst.py` 假 fallback、不读轨迹/Skill）按对齐结论整文件重写，不当成可演进基线。
- 前端入口先埋在页面底部且无创建按钮，等于看不见；后改为 Progress 后的独立面板，并加大字号、改卡片排版。

### 3. 遗留
- 诊断质量依赖真模型，本迭代测试全部 mock，未做真机标定。
- 多 Skill 的 batch 不出 patch（`suggested_patch = null`），只出文字归因。
- 诊断无历史版本，重复 analyze 覆盖同一文件。
- 批次调度仍是 `concurrency=1`（迭代 6 遗留）。
- GIS 拓扑诊断、断言自动修补仍不在范围内。
